# V3.2.0 任务生命周期与状态仓库改造方案（最终版）

## 1. 背景与目标

当前任务状态来自 `job_meta.json` / `checkpoint.json` / `queue_state.json` / 内存队列，存在多源不一致与推断兜底，导致前后端状态漂移与恢复失败。目标是建立**单一权威状态源**并完善**可恢复的预处理缓存体系**，实现队列顺序可恢复、前端状态一致、进度单调可预期。

**最终目标**：
- 任务状态唯一来源可追踪、可回放。
- 重启后队列顺序与任务进度可恢复且不会自动误执行。
- 预处理产物分层缓存可恢复，减少重复计算。
- 前端状态一致，进度不回退、不跳跃（除非明确重做）。

## 2. 设计原则

- **单一权威**：任务状态只从 SQLite 读写，禁止推断/扫描兜底。
- **原子提交**：预处理与检查点必须“先文件、后元数据”的原子提交。
- **分层缓存**：VAD/分诊/分离按层缓存，可恢复、可清理、可回滚。
- **进度单调**：默认单调递增，除非后端明确声明“重做/重置”。
- **低耦合**：新增模块以适配层方式接入，不侵入既有巨型类。

## 3. 核心机制概述

### 3.1 SQLite 状态仓库
- Task/QueueState/Checkpoint/TaskEvent/TaskHeartbeat 统一持久化。
- 自动创建 `jobs/task_state.db` 与表结构。

### 3.2 预处理缓存（默认保留）
- 产物落在 `jobs/{job_id}/cache_preprocess/`，默认保留。
- 统一输出层：无需分离的 Chunk 也输出到分离目录（硬链接或拷贝），便于后续一致读取。

### 3.3 进度体系（固定权重，可配置）
**固定总权重**，避免预设动态权重导致用户体验不一致。
- 预处理：30
- 转录：55（按模式分配）
- 精修/翻译：10（可跳过）
- 输出/收尾：5

预处理内部权重固定为 3:3:4（VAD/分诊/分离），在预处理权重内等比换算：
- VAD：9
- 分诊：9
- 分离：12

转录按模式分配（总和 55）：
- 纯快流：快流 55
- 低置信度复核（原“补刀”）：快流 35 + 复核 20
- 双流：快流 20 + 慢流 35

精修/翻译（总和 10）：
- 校对 6、翻译 4（未启用直接补满）。

## 4. 状态机定义

**允许的主状态流**：
- created → uploaded → queued → processing → finished
- processing → paused → queued → processing
- processing → failed / canceled
- queued → paused / canceled

**终态定义**：
- finished / failed / canceled

**重启纠偏规则**：
- 非终态任务统一记录 `reason=system_restart`。
- 运行中任务强制暂停并释放租约。
- 队列顺序必须恢复，且不自动继续执行。

## 5. 中断恢复流程

1. 启动加载 SQLite：Task/QueueState/Checkpoint/Heartbeat。
2. 执行重启纠偏：运行中任务暂停，租约清空，写事件。
3. 恢复队列顺序（QueueState），内存队列重建但不自动执行。
4. `/sync-tasks` 直接读仓库，前端统一显示一致状态。
5. 用户恢复任务时按原队列顺序入队，恢复进度不归零。

## 6. 预处理缓存与恢复策略（阶段零核心）

### 6.1 目录结构
```
jobs/{job_id}/cache_preprocess/
  manifest.json
  vad/
    vad_state.json
    chunks_metadata.json
    chunk_{idx}.wav
  triage/
    triage_results.json
  separation/
    chunk_{idx}.wav
    separation_stats.json
  separation_full/
    vocals_full.wav
    separation_full_state.json
```

### 6.2 原子写入与断电恢复
- 文件写入：`*.tmp` → `fsync` → `rename`。
- 元数据提交：写完文件后更新 `manifest.json`，标记完成。
- 恢复规则：
  - 文件存在但未完成标记：视为未完成，删除或重做。
  - 标记完成但文件缺失/校验失败：重做该 Chunk。

### 6.3 分层恢复逻辑
- **暂停在 VAD**：恢复 `vad_state.json` + `chunks_metadata.json`，从未完成段继续。
- **暂停在分诊**：
  - 顺序全量探测：记录已完成索引继续。
  - 中心扩散探测：记录探测序列、参数、游标与结果；不一致则重做探测。
- **暂停在分离**：以 Chunk 为原子，完成一个就写分离产物并删除对应 VAD 产物。
- **暂停在前处理完成后**：直接跳过预处理并恢复转录进度。

### 6.4 按需分离策略
- 无需分离 Chunk 写入 `separation/`（硬链接或拷贝），统一输出层读取。
- 写入完成后删除 VAD Chunk，降低重复占用与分支复杂度。

### 6.5 全局分离暂停确认
- 全局分离进行中：暂停需要二次确认。
- 用户确认后清理半成品分离结果并暂停；恢复时重新分离。

### 6.6 GC 与清理策略（默认关闭）
配置项：
- `cache_budget_gb`
- `ttl_hours`
- `max_tasks`
- `enable_preprocess_cache_gc`（默认 false）

行为：
- TTL > 预算 > 任务数，按 LRU 清理。
- 磁盘空间不足提醒前端，引导开启自动清理。
- **取消任务不清理**，**删除任务必须清理全部缓存**。

## 7. 分阶段实施计划

### 阶段零：预处理缓存与恢复体系（新增）
- 默认保留 VAD/分诊/分离产物。
- 断电恢复通过原子提交与 manifest 校验保证一致性。
- 统一输出层：无需分离 Chunk 进入分离目录。
- 中心扩散探测支持恢复序列与结果，不一致时重做。
- 全局分离暂停确认与清理策略。
- GC 机制（默认关闭）与磁盘空间提醒。

### 阶段一：队列恢复逻辑完善
- 重启后恢复队列顺序，不再清空队列。
- 运行中任务强制暂停；队列顺序保留，恢复时按顺序入队。
- 恢复任务进度不得归零（从检查点恢复）。

### 阶段二：前端状态一致性修复
- 状态来源收敛到仓库与 SSE，禁止前端推断。
- 状态更新带时间戳与版本校验，防止旧状态覆盖新状态。
- 进度单调规则：除非明确“重做/重置”，前端禁止进度回退。
- 进度条统一为单条总进度条，通过内嵌色带/文本展示子阶段与双流信息。

### 阶段三：文档与恢复策略说明
- 更新 llmdoc 架构与指南，删除过期逻辑描述。
- 记录断电、重启、暂停恢复的规范化流程。

## 8. 数据迁移与兼容

- `task_state.db` 不存在时自动创建并初始化表结构。
- SQLite 空库时自动扫描 `job_meta.json` / `checkpoint.json` / 任务目录导入。
- 队列状态由 `queue_state.json` 自动迁移到 SQLite。
- 已存在库不重复覆盖，仅对缺失任务幂等导入。

## 9. 测试与验收

- 预处理缓存：VAD/分诊/分离恢复、断电一致性、分离后删除 VAD。
- 全局分离：暂停确认与清理行为。
- 队列恢复：顺序恢复、进度保持、运行态纠偏。
- 前端一致性：状态不回退、进度不回退、断线恢复正确。

## 10. 风险与回滚

- 风险：缓存错误导致错误跳过阶段。
- 回滚：保留旧 `job_meta.json` 与 `checkpoint.json` 兼容读取逻辑。

## 11. 交付标准

- 状态仓库为唯一事实来源，恢复流程可追踪可回放。
- 预处理缓存可恢复，减少重复计算。
- 重启后队列顺序与任务进度恢复正确。
- 前端状态与进度一致，除显式重做外不回退。
