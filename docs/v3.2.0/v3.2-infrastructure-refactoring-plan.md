# V3.2.0 基础设施重构实施计划（按 Roadmap 对齐）

## 1. 目标与范围

**目标**：以 `docs/v3.2.0+/version-roadmap.md` 为准完成 V3.2.0 基础设施重构，做到用户无感知、可灰度、可回滚。

**范围内**：
- ASR 抽象接口 + 统一数据模型
- ModelManager V2（统一注册/加载/资源治理）
- 引擎适配器：SenseVoice / Whisper / DualStream / Dummy
- Worker 容器化：FastWorker/SlowWorker 只做模型推理
- 分句/对齐服务抽离：DefaultSegmenter、DefaultAligner
- AsyncDualPipeline / TranscriptionService 接入新接口

**非范围**：
- v3.2.1+ 语言检测、标点模型、Bridge 层、前端高亮等后续版本内容
- 新增外部 API（如引擎列表接口）与前端功能扩展

---

## 2. 架构对齐（现状 vs 目标）

### 2.1 现状（V3.1.2）

```
TranscriptionService
├─ if engine == "sensevoice": _sensevoice_process()
└─ if engine == "whisper": _whisper_process()

AsyncDualPipeline
├─ FastWorker（含分句/对齐/熔断相关逻辑）
├─ SlowWorker（含补刀逻辑与上下文拼接）
└─ AlignmentWorker
```

### 2.2 目标（V3.2.0）

```
TranscriptionService
└─ ASREngineFactory.create(...)

AsyncDualPipeline
├─ FastWorker（模型容器，仅推理）
├─ SlowWorker（模型容器，仅推理）
├─ DefaultSegmenter（旧分句逻辑封装为服务）
└─ DefaultAligner（旧对齐逻辑封装为服务）

ModelManager V2（统一模型注册/加载/资源治理）
```

**对齐原则**：
1. Worker 只做模型推理调用，不再内嵌分句/对齐逻辑。
2. 旧分句/对齐逻辑以“服务”形式保留，便于 v3.2.2+ 替换。
3. 所有模型实例只能通过 ModelManager V2 获取。

---

## 3. 关键设计对齐点（以 Roadmap 为准）

1. **ASR 抽象接口**  
   统一 `ASREngine`、`ASRResult`、`Segment`、`WordTimestamp` 等数据模型与能力枚举。

2. **ModelManager V2 统一治理**  
   - `ModelSpec` 统一描述模型（ONNX / PyTorch / 外部服务）。  
   - `ModelLoader` 抽象加载器（`OnnxLoader`、`TorchLoader`、`ExternalServiceLoader`）。  
   - 统一下载/校验流水线（优先打包模型，缺失时下载 + 哈希校验）。  
   - 资源治理：显存预算池 + CPU 调度器 + 设备分配接口。  
   - 可观测性：下载/加载耗时、使用频率、设备占用统计。  

3. **Worker 容器化**  
   - `FastWorker` 只负责：调用 draft 引擎、输出草稿（含 words/metadata）。  
   - `SlowWorker` 只负责：调用 patch 引擎、输出补刀结果。  
   - 分句/对齐逻辑移出 Worker，改由服务层处理。  

4. **分句/对齐服务抽离**  
   - `DefaultSegmenter`：封装旧 CTC/word-based 分句逻辑，接口 `segment(words, text, metadata)`。  
   - `DefaultAligner`：封装旧伪对齐逻辑，接口 `align(segments, words, metadata)`。  
   - 保持旧行为一致，确保 v3.1.2 → v3.2.0 质量无退化。

## 4. 分阶段实施计划

### Phase 1：ASR 核心与 ModelManager V2

**目标**：建立抽象接口，不影响现有功能。  

**任务 1.1：ASR 抽象接口与数据模型**  
- 新建：`backend/app/core/asr/*`  
- 要点：
  - `ASREngine` 抽象基类 + 能力枚举  
  - `ASRResult / Segment / WordTimestamp / ASRMetadata`  
  - `ConfidenceNormalizer / TimestampConverter`  

**任务 1.2：ASREngineFactory（工厂模式）**  
- 新建：`backend/app/engines/factory.py`  
- 约束：工厂类注释说明“工厂模式”与原因。  
  
**验收标准**：  
- ASR 抽象完整且可运行  
- 不修改现有转录功能的行为  
- 类型标注齐全，异常日志可追踪  

---

### Phase 2：引擎适配器

**目标**：封装现有 SenseVoice/Whisper 为 ASREngine，输出统一数据结构。  

**任务 2.1：SenseVoiceEngine**  
- 保留原始标签到 `metadata.raw_tags`（用于熔断/分句逻辑复用）。  
- 输出 `ASRResult`，确保 `words` 和 `confidence` 结构完整。  

**任务 2.2：WhisperEngine**  
- 置信度归一化使用 `ConfidenceNormalizer`。  
- 输出 `ASRResult`，确保 `segments` / `words` 对齐。  

**任务 2.3：DualStreamEngine**  
- 使用 draft 引擎的时间戳为权威，低置信度触发 patch。  
- 只做引擎级组合，不参与分句/对齐。  

**任务 2.4：DummyEngine**  
- 仅用于测试与流水线验证，避免依赖 GPU 模型。  

**验收标准**：  
- 适配器输出结构统一  
- SenseVoice 原始标签不丢失  
- 引擎可通过工厂创建  

---

### Phase 3：Worker 容器化与服务抽离

**目标**：让 Worker 成为纯模型容器，分句/对齐逻辑移至服务层。  

**任务 3.1：FastWorker 重构**  
- 仅负责：拉取 chunk → 调用 draft 引擎 → 输出草稿  
- 移除分句/对齐/熔断相关逻辑  

**任务 3.2：SlowWorker 重构**  
- 仅负责：调用 patch 引擎 → 输出补刀结果  
- 移除分句/对齐相关逻辑  

**任务 3.3：DefaultSegmenter / DefaultAligner 服务**  
- 抽离旧分句与旧对齐逻辑  
- 保持接口稳定：  
  - `segment(words, text, metadata)`  
  - `align(segments, words, metadata)`  

**验收标准**：  
- Worker 内无分句/对齐逻辑  
- 旧行为由服务层复现（质量差异 <2%）  

---

### Phase 4：流水线与服务适配

**目标**：让 AsyncDualPipeline / TranscriptionService 与新接口对接。  

**任务 4.1：AsyncDualPipeline 适配**  
- 注入 `FastWorker/SlowWorker` 引擎实例  
- 调用 `DefaultSegmenter` 与 `DefaultAligner` 完成分句/对齐  

**任务 4.2：TranscriptionService 适配**  
- 使用 `ASREngineFactory` 创建引擎  
- 保留旧配置映射（向后兼容）  
- 继续支持 `USE_NEW_ASR_ENGINE` 开关回滚  

---

### Phase 5：测试与回归

**单元测试**  
- ASR 核心模型与工具类  
- SenseVoice / Whisper / DualStream / Dummy  
- DefaultSegmenter / DefaultAligner  
- ModelManager V2 基础能力  

**集成测试**  
- DummyEngine + Worker + Pipeline（无模型环境）  
- SenseVoiceEngine / WhisperEngine 与原服务集成  

**回归测试**  
- 与 v3.1.2 结果对比（WER/CER 差异 <2%）  
- 性能差异 <10%  

---

## 5. 关键实现约束

1. **信息完整性**：SenseVoice 原始标签必须透传到 `metadata.raw_tags`。  
2. **工厂/策略注释**：核心工厂类需注明设计模式与原因。  
3. **异常不可静默**：捕获具体异常并记录上下文日志。  
4. **类型标注**：所有新/改动后端 Python 代码必须有类型标注。  

---

## 6. 风险与缓解

- **分句/对齐逻辑迁移风险**：旧逻辑抽离为服务时信息丢失  
  - 缓解：保留 metadata.raw_tags + 对比回归  
- **性能回退**：ModelManager 资源治理增加额外开销  
  - 缓解：基准测试 + 分阶段启用  
- **兼容性问题**：旧配置字段缺失  
  - 缓解：TranscriptionService 兼容映射  

---

## 7. 回滚策略
