最终优化方案（适配本项目架构，符合最佳实践）

A. 动态批处理（含降低批次门槛）

目标：让慢流 Whisper 在“可控等待”内持续获得批次输入，避免“长时间空闲 → 突发高占用”的波动。
具体做法（建议值为起点，需根据实际延迟/准确率微调）：
降低批次门槛：
min_batch_duration 从 20s → 6–10s
max_batch_duration 从 30s → 12–18s
min_batch_sentences 从 6 → 3–4
max_batch_sentences 从 10 → 6–8
starvation_timeout 从 5s → 1–2s
long_pause_threshold 从 2s → 0.8–1.2s
引入动态批处理策略：
设定 max_wait_ms（建议 200–500ms）
语音变长/ backlog 高时扩大批次；GPU 空闲或 backlog 低时快速 flush 小批次
以语音时长分桶（6–10s、10–15s、15–20s）避免 padding 浪费
B. 工作保守调度（Work-Conserving Scheduling）

目标：GPU 一旦空闲就有活干，且避免因批次门槛造成“无活可取”。
具体做法：
低/高水位调度：
当 queue_inter 低于低水位（例如 1–2）时，触发 Bridge 立即 flush
当 queue_inter 高于高水位（例如 4–6）时，允许扩批以提吞吐
GPU 空闲检测：
若 SlowWorker 空闲且 Bridge 缓冲非空，强制 flush（不等门槛）
预取与重叠：
SlowWorker 正在推理时，CPU 侧提前拼接下一批音频
减少“拼接时间 → GPU 空闲”的空窗
C. 模型常驻（Model Residency）

目标：避免模型被驱逐导致 GPU 空闲与冷启动抖动。
推荐策略（通过 model_runtime_config.json 或运行参数 API）：
Whisper 常驻并固定在 CUDA：
per_model.whisper.device = "cuda"
per_model.whisper.keep_resident = true
设置显存预算与预留：
global.max_vram_mb 设置为显存上限（或 0 表示不限制）
global.reserved_vram_mb 设置 256–1024MB（防止偶发峰值 OOM）
快流 SenseVoice 放 CPU：
transcription.sensevoice_device = "cpu"
避免 GPU 被快流争用
落地路径（建议）

先落地模型常驻（几乎零风险、收益立竿见影）
引入动态批处理 + 降低门槛（改善 GPU 波动的关键）
补齐工作保守调度（保证 GPU 不再“饥饿”）
效果预期（行业基准）

GPU 利用率更平滑：波动幅度明显降低
平均吞吐提升：批次化效率仍保留
延迟控制在预算范围内（例如 0.2–0.5s 等待换批）
