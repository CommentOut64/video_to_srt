# M5 收尾清理与发布验收方案

> Type: Architecture | Status: Active
> Version: V3.2.0+dev.20260213.07
> Scope: 清理历史补丁、参数收敛、文档一致性与最终验收

## 1. Summary

* **Goal**: 将 M1-M4 的增量改造收敛为稳定主链，删除过时逻辑，形成可发布状态。
* **完成定义**:
  - 旧硬边界补丁完全退场。
  - 参数集合收敛到软切/语义切分最小必需集。
  - 文档、测试、实现三者一致。

## 2. Diagram

* `M1-M4能力` -> `历史逻辑清理` -> `参数收敛` -> `全量回归` -> `发布候选`
* `代码真相` <-> `文档真相` 同步闭环

## 3. Key Components

* `backend/app/services/segmentation/boundary_processor.py`: 清理历史硬切分支。
* `backend/app/services/segmentation/segmentation_processor.py`: 保留软切主路径。
* `backend/app/services/text_pipeline_config.py`: 参数收敛入口。
* `backend/app/pipelines/mode_policy.py`: 三模式策略最终确认。
* `docs/v3.2.3/*.md` 与 `llmdoc/architecture/*`: 文档最终同步。

## 4. 清理范围

### 4.1 代码清理

1. 删除硬切直推相关逻辑（含历史 shift/force 补丁路径）。
2. 删除废弃字段和未被消费的兼容分支。
3. 删除重复实现（确保 NW 仅保留一套内核）。

### 4.2 参数清理

1. 移除互相冲突的历史阈值参数。
2. 收敛为软切/语义切分核心参数集。
3. 为每个参数补充默认值、边界与调参说明。

### 4.3 文档清理（Gardener Protocol）

1. 采用“整段替换”，禁止旧逻辑后追加补丁注释。
2. 删除 zombie docs（已失效方案章节）。
3. 保证文档体现当前状态，不写历史流水账。

## 5. 三模式最终验收

1. `dual_full`：完整软切 + 语义切分链路可用。
2. `smart_patch`：仅高置信 speaker_change 生效，其余保守退化。
3. `fast_only`：无 GPU 默认可用，流程可完整结束。

## 6. 回归测试清单

1. 功能回归：切分、对齐、替换、SSE 修订、暂停恢复。
2. 指标回归：漏切/错切/孤句/句中误切/额外切分。
3. 性能回归：TTFS、吞吐、GPU 峰值、修订延迟。
4. 数据一致性：trace 可追溯、deferred 有终态、无静默失败。

## 7. 发布闸门

1. 指标满足基线门槛且无 P0 回归。
2. 核心场景（单人、多人快切换、噪声场景）稳定。
3. 文档审阅通过，关键章节与代码路径一致。
4. 具备明确回退方案与回退开关。

## 8. 风险与应急

1. 风险：清理误删导致隐藏依赖断裂。  
应急：分批删除并配套回归，保留短期特性开关。
2. 风险：参数收敛后场景适配不足。  
应急：保留有限调参窗口与灰度策略。
3. 风险：文档未同步造成认知偏差。  
应急：发布前执行文档一致性检查清单。
