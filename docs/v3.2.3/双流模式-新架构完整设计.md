# 双流模式（Dual-Balanced）v3.2.3 新架构完整设计

> Type: Architecture | Status: Draft

## 1. Summary

* **Goal**：在最大复用现有代码（`PreprocessingPipeline` + `AsyncDualPipeline` 三循环 + L1-L7 Processor）的前提下，形成一条可落地、可回滚、可维护的“双流定稿”主链路，重点提升多人对话场景的字幕切分稳定性，并控制首条字幕等待与 GPU 利用率。
* **核心原则**：
  - **快流=时间主时钟**：以 SenseVoice 字/词级时间戳作为最终时间锚点（Time Master）。
  - **慢流=内容主来源**：Whisper 作为内容质量来源（Content Master），通过 L4 对齐挂载到快流时间轴。
  - **说话人/分段=结构时间线信号**：声纹聚类（现有）+ 可选 Pyannote segmentation（新增/异步）提供 speaker/time 边界信号，驱动 Bridge flush 与 L6 硬边界（Structure Signals）。
  - **低延迟优先**：Pre-L0 不允许阻塞首条字幕；任何新增模型必须提供开关与回退路径。
  - **8GB 显存可运行**：SenseVoice 常驻；Whisper 常驻于转录期；Pyannote/LLM 仅按需串行加载，避免峰值爆显存。
* **与 `llmdoc/architecture/text-processing-v3.2.3-evaluation.md` 的一致性**：
  - Pre-L0 的 Pyannote 必须异步（不阻塞首条字幕）。
  - LLM 不允许全量替代 L6 主切分，仅做“难例稀疏精修”。
  - 标点模型不作为硬依赖，允许默认关闭；断句稳定性必须来自“多信号边界”。

### 2.2 三路信号“对齐关系图”（避免误解）

```text
物理时间轴（秒）──────────────────────────────────────────────────────────▶

快流 SenseVoice：  words(time)  ────────────┐  (时间主锚点)
慢流 Whisper：     text(content) ── L4 文本对齐 ──┼──> 对齐到快流 words(time)
结构信号 Pyannote：speaker_track(time) ──────┘  (只做时间贴标，不做文本匹配)

结论：
 - 快流↔慢流：文本对齐（L4），输出挂载到快流时间轴
 - 快流↔Pyannote：时间对齐（按时间段贴 speaker_id/turn）
 - 慢流↔Pyannote：时间对齐（用于 flush/边界信号，非文本匹配）
```

* 预处理（现有）：
  - `backend/app/pipelines/preprocessing_pipeline.py`：Stage 2 频谱分诊、Stage 3 人声分离、Stage 4 LangID、Stage 5 声纹、Stage 6 聚类（顺序已满足“分离→声纹”依赖）。

  - `backend/app/pipelines/stages/separation_stage.py`：Demucs 分离（支持 `separation_mode=on_demand`）。
  - `backend/app/services/preprocess_cache_service.py`：triage/separation/langid/speaker 缓存与断点恢复。
* 双流主干（现有）：
  - `backend/app/pipelines/async_dual_pipeline.py`：fast/slow/align 三循环；Bridge 接入；L1-L7 Processor 编排；批处理回写。
  - `backend/app/services/punctuation/semantic_buffer.py`：快流语义缓冲与短句合并、flush（含 speaker_change 触发）。
  - `backend/app/services/bridge/bridge_controller.py`：Bridge 批次调度、flush 规则（speaker/language/pause/starvation/idle）。
  - `backend/app/services/punctuation/final_splitter.py`：L6 最终切分（停顿/长度/弱标点等）。
  - `backend/app/services/punctuation/punctuation_processor.py`：L3 标点候选融合（可降级或关闭，不作为硬依赖）。
* 新增（v3.2.3 目标）：
  - `PyannoteSegmentationService`（新增模块，建议放在 `backend/app/services/pyannote/`）：滑窗 segmentation，输出 speaker_track/turn。
  - `PreciseTimelinePatch`（新增数据结构，建议放在 `backend/app/models/`）：描述更稳定的 turn 边界与 speaker_remap。
  - `SparseLLMRefine`（新增模块，建议放在 `backend/app/services/llm_refine/`）：难例门控 + LLM 输出校验 + LCS 回填（不改时间锚点）。

# 新增内容的详细描述（v3.2.3）

## 4. Pre-L0 流程设计（在现有预处理架构上扩展）

### 4.1 目标与边界

* **目标**：在多人对话场景提供稳定的 speaker_change 信号与更干净的声纹 embedding（基于人声分离产物），用于：
  - Bridge 以 speaker_change 强制 flush，避免多人混在一个 batch；
  - L6 以 speaker hard-boundary 强制切分，降低“该断不断/不该断乱断”；
  - 可选的 Pyannote segmentation 进一步修正 turn 边界（异步，不阻塞首条字幕）。
* **边界**：
  - Pre-L0 不允许引入“全片阻塞等待”，否则首条字幕等待会失控。
  - 预处理必须兼容现有缓存/断点恢复（`PreprocessCacheService`）。

### 4.2 现有阶段（与代码一致的顺序）

按 `preprocessing_pipeline.py` 的阶段顺序（已满足你要求的链描述）：

1. **音频提取**（Stage 1a）
2. **VAD 切分**（Stage 1b，产出 `chunks` + `vad_intervals`）
3. **频谱分诊**（Stage 2，标记 `needs_separation`）
4. **人声分离**（Stage 3，Demucs，建议 `on_demand`）
5. **语言检测**（Stage 4，失败不阻断）
6. **声纹提取**（Stage 5，必须基于分离后的人声）
7. **在线聚类**（Stage 6，生成 `primary_speaker_id` 与切换信号）

### 4.3 on_demand 人声分离与“分离→声纹”的依赖满足方式

* **硬约束**：声纹提取必须基于分离后音频（vocals）。
* **建议实现口径（最小改动）**：
  - 分离阶段将 `chunk.audio` 替换为 vocals（或新增 `chunk.vocals_audio` 并在声纹提取时优先使用）。
  - 声纹提取阶段只读取 vocals（若缺失则降级到原音频，并打质量标记，供后续门控）。

### 4.4 Pyannote segmentation 的接入方式（新增，必须异步）

* **为何必须异步**：全片 segmentation + 全局聚类会显著拉长首条字幕等待（评估报告已给出风险）。
* **异步策略**：
  - 在预处理阶段启动 `PyannoteSegmentationTask`，但不等待它完成；
  - 它产出 `PreciseTimelinePatch`：
    - `speaker_turns`（start/end/speaker_global_id）
    - `speaker_remap`（将在线聚类的 speaker_id 映射为更稳定的全局ID）
    - `boundary_patch`（在 turn 边界处建议强制切分）
  - 只允许回写“尚未定稿”的 chunk（避免字幕抖动）。

## 5. 双流转录与后处理的时序设计（按批交错）

### 5.1 关键队列与批概念

* **chunk**：VAD 切块后的最小处理单元。
* **SemanticChunk**：快流语义缓冲输出的句子集合（可跨 chunk 轻微合并，但受 hard_limit 约束）。
* **BridgeBatch**：Bridge 聚合的 Whisper 批次（批内保持单语言、单说话人段优先）。
* **三循环**：
  - `fast_loop`：产生草稿与语义信号
  - `slow_loop`：消费 `BridgeBatch` 做 Whisper 批推理并回写
  - `align_loop`：对每个完成慢流回写的 chunk 执行 L2-L7 定稿

### 5.2 交错原则（减少等待 + 提升 GPU 效率）

* **草稿先行**：fast_loop 产出即推送（SSE）。
* **慢流按批**：BridgeBatch 尽量减少 Whisper 调用次数，提高吞吐与上下文一致性。
* **定稿顺序提交**：align_loop 乱序执行但顺序提交，避免时间轴错乱。
* **后处理批内触发**：一个 BridgeBatch 覆盖的 chunk 集合完成 L2-L7 后，立刻进入“批级后处理”（CPU 优先），而不是等全片结束。

## 6. 流程设计（你指定的完整链描述：逐步产物与依赖）

### 6.1 端到端链（Dual-Balanced）

1) **音频提取**  
输出：`full_audio_array/full_audio_sr`

2) **VAD 切分**  
输出：`chunks` + `vad_intervals`

3) **频谱分诊**  
输出：`needs_separation`（逐 chunk）+ triage 统计

4) **人声分离（Demucs，GPU 优先）**  
输出：vocals（替换或挂到 chunk）

5) **语言检测（LangID）**  
输出：`chunk.language`（供 Bridge 语言切换 flush 与策略选择）

6) **声纹提取（Embedding，基于 vocals）**  
输出：`chunk.speaker_embedding`

7) **在线聚类（Clustering）**  
输出：`chunk.primary_speaker_id` + `is_speaker_changed`（防抖后）

8) **快流（SenseVoice）**  
输出：草稿字幕 + `sv_words(time)` + `TextTrack`

9) **SemanticBuffer**  
输入：快流文本/标点候选/停顿/说话人信号  
输出：`SemanticChunk(sentences, audio_range, speaker_id, language)`

10) **Bridge**  
输入：`SemanticChunk`  
输出：`BridgeBatch(audio_segments + sentences + prompt_context)`  
flush：speaker_change / language_change / long_pause / starvation / idle

11) **慢流（Whisper 批处理）**  
输入：`BridgeBatch`（拼接音频，保留间隔）  
输出：`whisper_result` 回写至 batch 覆盖的 contexts

12) **后处理主链路（L1-L7，现有）**  
L1 规范化 → L2 仲裁 → L3（可选）→ L4 对齐 → L5 注入 → L6 切分 → L7 输出  
输出：定稿 `SentenceSegment[]`（替换草稿并落盘）

13) **LLM 切分/标点精修（可选，新增）**  
输入：L6 输出中的难例片段（门控）  
输出：文本/分行建议（不改时轴），校验失败即回退  
推送：作为“定稿二次替换”或“编辑层建议”

14) **推送（SSE/编辑器/落盘）**  
草稿：尽早推送；定稿：按 chunk replace；精修：按需二次 replace（可选）

## 7. GPU/CPU 资源与模型常驻策略（避免频繁装卸且不爆显存）

### 7.1 默认策略（8GB 显存：串行调度）

* 常驻：SenseVoice（小）+ OS/CUDA
* 转录期常驻：Whisper（优先级最高）
* 仅按需串行：Demucs / PyannoteSegmentation / LLM（用完即卸，且不与 Whisper 并行抢显存）

### 7.2 12GB+ 策略（并行常驻）

* SenseVoice + Whisper 可并行常驻
* Demucs/LLM 仍建议按需加载（减少峰值与抖动）

### 7.3 无 GPU（Accuracy-first 回退）

* 关闭 Pyannote segmentation（CPU 性价比差）
* Whisper 作为内容主来源（慢但稳），快流仅做时间锚点/兜底
* Demucs 仅在频谱分诊强提示时才启用（避免全片 CPU 分离拖死）
* LLM 默认关闭（CPU 代价过高且回填风险不值得）

## 8. 标点模型与 LLM 的最终定位（落实“可放弃依赖”）

### 8.1 标点模型

* **默认不依赖**：L6 必须在“无标点/低标点覆盖率”时仍稳定切分（靠停顿/长度/说话人硬边界）。
* **保留为备用方案**（可选开关）：
  - 草稿可读性；
  - 边界弱信号（非硬依赖）；
  - 弱设备/无 LLM 的低成本兜底；
  - 质量监控特征（coverage、弱标点密度）。

### 8.2 LLM（仅稀疏精修，不进入主切分）

* **触发门控**：超长句风险、边界置信低、映射覆盖率低、多说话人冲突高。
* **输出约束**：只允许加标点/换行/极轻量格式修复；删改率超阈值直接丢弃回退。
* **时间戳原则**：不改 L4/L6 的时间锚点；仅在文本层做二次替换或建议。

## 9. 接入现有架构的初步方案（P0-P3，先易后难，可回滚）

### 9.1 P0（低风险快收益：边界稳定性收口）

* **目标**：先解决“多人对话超长字幕/错断”。
* **改动点（最小侵入）**：
  - 让 `chunk.primary_speaker_id` 贯穿到 `SemanticBuffer -> SemanticChunk -> Bridge -> L6`，并在 L6 增加 speaker hard-boundary（不同 speaker 必断，禁止跨 speaker 合并）。
  - Bridge flush 优先级明确化：speaker_change > language_change > long_pause > threshold。
  - 运行参数补齐：新增 `bridge.*`、`speaker_policy.*`（用于前端调参/回滚）。

### 9.2 P1（预处理升级：异步 Pyannote + 全局聚类精修）

* **目标**：进一步提升多人对话一致性，但不增加首条字幕等待。
* **落地方式**：
  - 新增异步任务产出 `PreciseTimelinePatch`，仅回写未定稿 chunk 的 speaker 边界信号；
  - 允许开关关闭，完全回退到现有在线聚类。

### 9.3 P2（对齐增强：中英软匹配）

* **目标**：提升对齐稳定性，减少对“标点存在”的依赖。
* **策略**：中文拼音软匹配/英文更强编辑距离匹配（按语言开关，失败可回滚）。

### 9.4 P3（稀疏 LLM 精修）

* **目标**：在可控成本下提升难例可读性（不破坏时轴）。
* **策略**：仅难例触发、强校验、回填失败回退，且在 GPU 空闲窗口执行。

## 10. 验收与可观测性（保证不中途停摆）

* **延迟类**：首条字幕等待 P50/P95 不超阈值；BridgeBatch 平均等待时长不劣化。
* **切分质量类**：超长句率下降、多人对话错断率下降、`avg_boundary_f1` 达标。
* **稳定性类**：新模型不可用/显存不足时必须自动回退（任务不失败）。
* **可回滚**：每个 P 阶段都必须有一键关闭开关与旧路径回退。
