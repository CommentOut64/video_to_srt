# P0-L0-L8 断点与任务生命周期彻底修复方案

> 版本：V3.2.0+dev.20260219.01  
> 状态：Draft（可执行）  
> 范围：后端任务状态机、断点恢复控制面、队列执行模型、前后端实时同步、取消/删除收敛

## 1. 一句话结论

当前系统不是“不可用”，而是“控制面不一致”；需要做**分阶段局部重设计**，先止血，再统一状态机与断点控制面，最后升级执行模型以获得真正可控的取消/删除。

---

## 2. 现状问题归并

### 2.1 已确认问题

1. 断点恢复不完整  
- `runtime_state.db` 优先策略覆盖了 `checkpoint.json` 中转录细粒度字段，导致恢复语义丢失。

2. 生命周期状态收敛不稳定  
- `CancelledException/PausedException` 在部分路径先被映射为 `failed`，再被上层改写，状态信号存在抖动窗口。

3. 前后端同步存在缺口  
- 前端单任务 SSE 未覆盖 `signal.job_canceling`/`signal.job_force_canceled`。  
- 编辑器取消后过早断开 SSE，容易长期停留在“正在取消”。

4. 队列“超时放行”与实际执行模型不一致  
- 当前 worker 为单线程阻塞执行，`running_job_id=None` 并不等于“下个任务可启动”。

5. 取消点分布不均  
- 大原子区（如全局分离）会放大“取消响应时延”，并拖累删除/队列推进体验。

---

## 3. 目标与非目标

### 3.1 目标（必须达成）

1. 生命周期全链路可收敛  
- 任意任务最终只能进入一个终态（`finished/failed/canceled/force_canceled/removed`）。

2. 断点恢复语义完整  
- 预处理边界状态、转录细粒度状态、字幕快照可同时恢复，且优先级规则明确可测。

3. 前后端实时一致  
- 取消、删除、暂停、恢复在 UI 与后端状态仓库之间无长期分歧。

4. 队列推进可证明  
- 取消/删除不会长期阻塞后续任务；阻塞时必须有可观测原因与超时策略。

5. 可回归、可灰度  
- 每阶段都具备单测+集成验收与回滚边界。

### 3.2 非目标（本轮不做）

1. 不做转录算法重构（ASR/对齐策略本身不在本方案范围）。  
2. 不做前端 UI 视觉重构，仅做状态同步与交互语义修复。  
3. 不一次性迁移所有旧任务历史数据，只提供兼容读取与渐进迁移。

---

## 4. 设计原则

1. 单一事实源  
- 状态仓库为任务状态真源，SSE/API 仅为其投影。

2. 显式状态机  
- 所有状态迁移必须经过“合法边检查 + 原因记录 + 时间戳/序号”。

3. 控制面与数据面分离  
- `runtime_state.db` 承担控制面（单元边界/控制信号），`checkpoint.json` 承担数据面（转录细节/字幕快照），恢复时执行可配置合并。

4. 协作式取消优先，强制取消兜底  
- 先边界停机，再强制回收；强制回收必须与执行模型一致，不能只改内存标志。

5. 分阶段可交付  
- 每阶段都能独立上线并降低用户可见问题。

---

## 5. 分阶段修复路线

## Phase 0（P0，止血）状态契约冻结与可观测性补齐

### 目标

先把“看不见、说不清、复现难”的问题变成可追踪问题。

### 主要改动

1. 固化状态机字典与迁移白名单  
- 新增统一状态常量与合法迁移表（后端）。  
- 对非法迁移打错误日志并拒绝落库。

2. 给状态事件加序号  
- 每次状态迁移附加 `state_seq`、`updated_at`、`reason`。  
- SSE/API 都透传，前端按序应用，避免旧事件覆盖新状态。

3. 关键日志补齐  
- 取消链路增加阶段耗时与“卡住点”日志：请求时间、进入 canceling 时间、终态时间。

### 验收标准

1. 任意任务都能在日志中还原完整状态迁移链。  
2. 前后端状态冲突可定位到具体事件序号。  
3. 不改变现有业务行为，仅增强可观测性。

---

## Phase 1（P0，收敛）取消/删除生命周期修复

### 目标

彻底解决“正在取消卡住”“删除后状态不收敛”“后续任务不启动（表象）”。

### 主要改动

1. 异常语义分层  
- `CancelledException/PausedException` 在编排层不再先标记 `failed`。  
- 统一由队列层做终态映射，避免失败信号误发。

2. 单任务 SSE 信号补齐  
- 前端订阅并处理：`signal.job_canceling`、`signal.job_force_canceled`。  
- 编辑器取消后不立即 `cleanupSSE`，收到终态信号后再断连。

3. `canceling` 兜底机制  
- 前端对 `canceling` 增加超时轮询：超过阈值自动拉 `/api/status/{job_id}` 与 `/api/sync-tasks`。

4. 删除语义标准化  
- 运行中删除返回统一结构：`pending_delete=true` + 当前状态。  
- 删除失败不再回落 `paused`，改为 `canceling` + 明确 `delete_blocked` 原因码。

### 验收标准

1. 运行中取消后，前端不再长期卡 `canceling`。  
2. 运行中删除后，任务可稳定进入 `removed` 或 `delete_blocked`（可重试）状态。  
3. 取消链路不再发送错误的 `job_failed`。

---

## Phase 2（P1，控制面对齐）断点恢复双源合并策略

### 目标

恢复路径同时保留“单元边界控制”与“转录细粒度数据”。

### 主要改动

1. 新增恢复合并器 `ResumeStateMerger`  
- 输入：`runtime_state.db` + `checkpoint.json`。  
- 输出：完整 `ResumeContext`（包含 `safe/slow/finalized/sentences_snapshot`）。

2. 定义恢复优先级规则  
- 预处理完成位：`runtime_state.db` 优先。  
- 转录细粒度字段：`checkpoint.json` 优先。  
- 冲突时记录 `merge_decision` 到日志与诊断信息。

3. 扩展 `RuntimeCheckpointSnapshot`（最小必要）  
- 追加可选 `transcription_hint`（不复制全部 checkpoint，仅存关键索引摘要）。

### 验收标准

1. 暂停后恢复不丢 `finalized_indices/sentences_snapshot`。  
2. 重启恢复时预处理阶段不会倒退重跑已提交单元。  
3. 合并决策可追踪、可单测覆盖。

---

## Phase 3（P1，执行模型重构）队列调度与执行解耦

### 目标

让“强制取消超时放行”从逻辑放行变成真实放行。

### 主要改动

1. 队列线程变为纯调度器  
- 执行器改为独立运行单元（建议进程级 JobRunner）。  
- 调度器管理 slot，占用/释放由 runner 生命周期回调驱动。

2. 强制取消升级  
- 协作式取消超时后，调度器触发 runner 强制终止。  
- 只有 runner 确认退出，slot 才释放并启动下个任务。

3. 资源回收闭环  
- 模型/子进程清理与 runner 绑定，避免“状态已取消但资源仍占用”。

### 验收标准

1. 取消超时后，下一个任务可实际启动（非仅状态变化）。  
2. 不出现同 GPU 并发转录导致的资源争抢回归。  
3. 队列吞吐与稳定性不低于当前基线。

---

## Phase 4（P1，前端收口）单一状态投影与实时同步

### 目标

消除 `progressStore` 与 `taskStore` 双源分叉。

### 主要改动

1. 明确数据主线  
- 统一由 `taskStore` 接收全局状态事件，`progressStore` 仅处理进度细节并引用同一 `state_seq`。

2. 统一终态处理  
- `canceled/force_canceled/removed` 在编辑器、任务列表、监视器组件表现一致。  
- 终态后才清理单任务 SSE。

3. 周期性轻量同步  
- App 级增加低频 `syncTasksFromBackend()`（如 60s），仅在 SSE 健康异常或关键状态滞留时触发。

### 验收标准

1. 前端不再出现“列表已取消、编辑器仍正在取消”。  
2. `job_removed` 后任务不会“复活”。  
3. 断线重连后状态可自动收敛。

---

## Phase 5（P0/P1 验收）测试矩阵与灰度发布

### 目标

把本次问题从“经验修”升级为“可回归”。

### 必测矩阵

1. 任务阶段取消点  
- 预处理：FFmpeg、频谱分诊、全局分离、按需分离、LangID。  
- 转录：Fast、Slow、Align、Finalize。  
- 每个阶段验证：取消响应时间、终态、队列推进、断点可恢复。

2. 生命周期场景  
- 运行中取消、运行中删除、排队取消、排队删除、暂停后恢复、重启后恢复。

3. 前后端一致性  
- SSE 正常、SSE 断连、SSE 延迟、HTTP 兜底。

### 发布策略

1. 灰度开关  
- `LIFECYCLE_V2_ENABLED`、`RESUME_MERGE_ENABLED`、`RUNNER_ISOLATION_ENABLED` 分阶段放量。

2. 回滚策略  
- 任一阶段异常可按开关回退到上一稳定实现。

## 6. 状态机规范（目标态）

### 6.1 状态集合

`created -> queued -> processing -> (pausing -> paused -> queued) | (canceling -> canceled|force_canceled) | finished | failed`  
删除路径：`{queued,paused,canceled,force_canceled,finished,failed} -> removed`

### 6.2 关键约束

1. 终态唯一且不可逆。  
2. `canceling` 必须在超时阈值内收敛到 `canceled` 或 `force_canceled`。  
3. `removed` 仅在资源清理成功后进入。  
4. 任一状态迁移必须写事件（含 `state_seq`）。

## 8. 风险与应对

1. 执行模型重构风险最高  
- 应对：先做 Phase 0/1/2 收敛，再灰度 Phase 3。

2. 历史任务兼容风险  
- 应对：保留旧 checkpoint 读取路径，新增合并器仅增强不破坏。

3. 前端状态治理回归风险  
- 应对：先做信号补齐，再做 store 收敛，最后清理旧分支逻辑。

---

## 9. 推荐推进顺序（现实可落地）

1. 先做 Phase 0 + Phase 1（1~2 个迭代）  
- 立即消除用户最痛点：卡 `canceling`、删除不收敛、状态错乱。

2. 再做 Phase 2（1 个迭代）  
- 解决断点恢复“看似可恢复但丢细节”的根问题。

3. 最后做 Phase 3 + Phase 4 + Phase 5（2~3 个迭代）  
- 完成执行模型升级和长期稳定性建设。

---

## 10. 完成定义（DoD）

1. 线上 7 天无“任务长期停留 canceling 超阈值”告警。  
2. 取消后队列推进成功率达到 99.9%+。  
3. 暂停/重启恢复后字幕与进度恢复一致性通过回归矩阵。  
4. 前端状态与后端状态仓库一致率达到 100%（按 `state_seq` 采样校验）。
